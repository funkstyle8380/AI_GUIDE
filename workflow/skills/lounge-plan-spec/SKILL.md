# lounge-plan-spec — 화면·정책 설계

## 역할과 선택 기준

화면과 업무 규칙을 개발·디자인·QA가 같은 의미로 읽을 수 있게 쓰는 단계다. "이 메뉴 화면설계서 초안 잡아줘", "취소 정책 정의해줘", "설계서에 빠진 상태 찾아줘", "현업 확인 요청 써줘" 같은 요청에 사용한다. AI가 사업 정책을 대신 결정하는 단계는 아니다.

## 필요한 입력과 조사 범위

- 필수: 대상 화면 ID 목록(IA 기준)과 설계 범위, 관련 요구.
- 관련 근거: IA·대조표, 기존 설계서·Figma, 공통 정책 정의, 결정 기록, 디자인 가이드. 실제로 있는 것만 쓴다.
- 범위: 대상 화면과 직접 연결된 전후 화면, 같은 정책을 쓰는 다른 화면.

## 적용과 입력

[루트 지침](../../../AGENTS.md)과 프로젝트의 설계서 템플릿을 적용한다. 템플릿이 없으면 [화면설계서 기준](../../planning.md#screen-spec)의 항목으로 시작한다.

## 작업

1. 대상 화면이 IA에 있는지 확인한다. IA에 없는 화면이 필요하면 설계 전에 IA 반영을 요청한다.
2. 화면마다 화면 정보·구성 요소·상태·동작·입력 검증·정책 참조·미정 항목을 채운다. 빈 항목은 '해당 없음'과 '미정'을 구분한다.
3. 여러 화면에서 쓰는 규칙은 정책 정의로 분리하고 화면에서는 정책 ID로 참조한다.
4. 상태가 있는 대상(이용권·주문·프로모션·승인 요청)은 상태 목록과 전이 조건을 표로 정리하고, 각 상태에서 화면에 보이는 버튼·문구를 연결한다.
5. 오류·빈 상태·권한 없음·외부 연동 실패 때 사용자가 보는 결과를 빠뜨리지 않는다.
6. 결정이 필요한 항목은 결정 주체별로 나눠 확인 요청 초안을 만든다. 초안만 요청받았으면 보내지 않는다.
7. 결정 전 임시 가정으로 설계한 부분은 '가안'으로 표시한다.

산출물: 화면설계서 / 정책 정의 / 상태 전이표 / 확인 요청 초안 / 가안 목록.

## 설계 판단을 구체화하는 방법

- 버튼 하나마다 "누르면 무엇이 바뀌고, 실패하면 무엇을 보여주는가"를 적는다.
- 목록 화면은 기본 정렬·검색 조건·페이지 크기·엑셀 다운로드 범위를 적는다.
- 같은 대상의 이력은 별도 화면보다 상세 화면의 탭으로 두는 방식을 먼저 검토한다. 프로젝트 원칙이 있으면 따른다.
- 채널별로 동작이 다를 때만 차이를 적고, 같은 내용을 채널마다 반복하지 않는다.
- 데이터 출처·계산 방식이 불분명하면 화면에서 확정하지 않고 개발 협의로 남긴다.

## 미정과 다음 단계

정책 하나가 미정이라고 메뉴 전체를 멈추지 않는다. 상태 정의나 승인 흐름처럼 여러 화면을 바꾸는 미정은 해당 화면 묶음을 보류하고, 화면 골격·공통 영역·독립 흐름은 진행한다. 완성된 설계서는 lounge-plan-review로 검수한다.

## 결과 형식과 사용 예시

```text
설계 범위·근거: <화면 ID 목록 / IA·요구·결정 근거>
작성·수정한 화면: <화면 ID / 상태: 확정·가안·보류>
정책 정의: <정책 ID / 적용 화면 / 미정 항목>
확인 요청: <질문 / 결정 주체 / 영향 화면 / 보류 범위>
개발 협의: <데이터 출처·연동·처리 방식 질문>
```

가상 사례: 프로모션 등록 화면을 설계하는데 승인 후 수정 가능 여부가 정해져 있지 않다. 등록·조회 화면의 입력 항목은 설계를 진행하고, 승인 후 상태의 '수정' 버튼 노출과 재승인 흐름은 보류한다. 현업에는 "승인된 프로모션을 수정하면 재승인이 필요한가요, 수정 자체를 막나요?"를 묻는다. 실제 정책이 아니다.

## 기록과 연결

[공유 기록 기준](../../README.md#shared-records)에 따라 작업·결정 기록을 갱신한다. 확인 요청을 보냈다면 결정 항목에 링크를 연결하고, 답변을 받으면 설계서 반영 여부를 함께 기록한다.
