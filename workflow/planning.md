# 기획 작성·검토 기준

이 문서는 기획 작업에서 확인할 항목을 정리한 기준이다. 모든 항목을 매번 적용하지 않고 이번 작업에 해당하는 절만 읽는다. 실제 양식·ID 체계·승인 절차는 프로젝트에서 합의한 기준이 우선하며, 이 문서와 다르면 차이와 영향 범위를 기록한다.

## 범위와 기존 산출물

더라운지 3.0은 APP·FO(웹)·BO와 현장운영(OO)·파트너오피스(PO)에 걸친 재구축이다. 작업 전에 대상이 어느 영역·채널·모듈인지, 기준 자료가 어느 파일의 어느 버전인지 확인한다. 같은 이름의 파일이 여러 버전으로 돌면 최신 승인본·작업본·참고본을 먼저 구분하고, 결과에 사용한 파일명과 버전을 남긴다.

기존 산출물(AS-IS IA, TO-BE IA, 대조표, 설계서)이 있으면 새로 만들기 전에 재사용할 수 있는지 본다. 이전 결과를 이어받을 때는 어떤 판정을 승계했고 어떤 것을 새로 판단했는지 구분한다.

<a id="project-docs"></a>
## 권장 확장 — 프로젝트 기획 문서 연결

용어집·ID 규칙·공통 정책처럼 반복해서 쓰는 내용이 정리돼 있으면 문서 목차에서 이번 작업에 필요한 부분만 읽는다. 없으면 존재한다고 가정하지 않고, 반복되는 설명이 생길 때 [프로젝트 기획 문서 운영](project-docs.md)에 따라 만든다.

<a id="xlsx-input"></a>
## 엑셀(IA·대조표)로 전달받은 자료 읽기

IA와 대조표는 대부분 엑셀로 오간다. 파일을 열었다고 내용을 모두 읽은 것은 아니다.

1. **구조 파악:** 시트 목록, 각 시트의 머리글 행, 데이터 행 수를 먼저 확인한다. 표지·변경 이력·작성 기준 시트가 있으면 함께 읽는다.
2. **읽기 범위 확인:** 숨김 시트·숨김 행/열, 필터가 걸린 상태, 병합 셀, 다른 시트를 참조하는 수식을 확인한다. 병합 셀은 상위 메뉴명이 아래 행에 비어 보이게 만들므로 채워서 해석한다.
3. **ID·이름 대조:** 화면 ID의 중복·누락, 같은 화면이 다른 ID로 두 번 나오는 경우, 표지에 적힌 총 본수와 실제 행 수가 맞는지 확인한다. 차이는 수정하지 말고 품질 이슈로 기록한다.
4. **결과 산출:** 원본은 보존하고 결과는 별도 파일로 만든다. 결과 파일에 원본 파일명·시트·버전, 작성 기준, 요약 시트를 둔다.

시트명이 요청과 다르면(예: 요청한 시트가 없고 비슷한 이름의 시트만 있음) 임의로 대체하지 말고 어느 시트를 썼는지 명시한다.

<a id="ppt-input"></a>
## PPT 보고서·기획서 읽기

PPT는 파일명·버전과 대상 슬라이드 번호·제목을 지정해 읽는다. 큰 보고서는 목차와 전체 흐름을 먼저 파악하고, 대상 기능의 슬라이드만 상세히 읽는다.

- 본문·표·발표자 노트와 화면 이미지·도형·화살표를 함께 확인한다. 텍스트만 추출됐다면 화면 배치나 흐름까지 읽었다고 보지 않는다.
- 같은 보고서 안에서 일정·범위가 슬라이드마다 다르게 적혀 있으면 충돌로 기록하고 확정본을 확인한다.
- 이미지 안의 글자·첨부 캡처는 도구에 따라 누락될 수 있다. 읽지 못한 슬라이드는 미확인으로 남긴다.

<a id="figma-input"></a>
## Figma 화면설계 연결과 접근 오류

Figma를 직접 읽는 작업은 사용하는 도구의 실제 연결 방식(MCP·REST API)과 접근 권한을 먼저 확인한다. 화면 하나에서 화면 이름과 주요 문구를 읽어 연결을 검증한 뒤 범위를 넓힌다.

- 403: 계정의 파일 접근 권한과 인증 범위를 확인한다.
- 429·부분 응답: 호출 한도나 응답 크기 문제다. 실패한 대규모 조회를 반복하지 않고 범위를 줄인다.
- 연결이 없으면 화면 캡처·PDF로 대체할 수 있다. 이 경우 원본에서 확인하지 못한 주석·상태·프로토타입 연결은 미확인으로 남긴다.

<a id="figma-scope"></a>
## 읽기 범위·컨텍스트 관리

화면 하나는 범위가 명확하지만 전후 흐름이 빠지기 쉽고, 메뉴 전체는 흐름을 보기 좋지만 읽는 양이 크다. 메뉴 전체를 맡길 때도 **구조·화면 목록 확인 → 우선 화면 묶음 상세 확인 → 근거·미정 기록 → 다음 묶음** 순서로 나눈다. 묶음마다 결과를 기록해 두면 앞서 읽은 내용이 대화에서 밀려나도 다시 찾을 수 있다. 구조만 본 상태와 상세 검토 완료를 구분한다.

<a id="ia"></a>
## IA 작성 기준

<a id="ia-unit"></a>
### 화면 단위

IA의 한 행은 사용자가 보는 하나의 화면 상태를 뜻한다. 메뉴 단위로만 적으면 설계·개발·테스트 범위를 셀 수 없다.

| 대상 | 처리 | 이유 |
| --- | --- | --- |
| 일반 화면·레이어 팝업·바텀시트 | 화면으로 등록 | 별도 설계·개발 대상 |
| 외부 화면(PG 결제창, 본인인증, 외부 링크) | 제외 또는 '외부'로 구분 | 우리 쪽에서 설계하지 않음 |
| 화면 없는 로직(자동 로그인, 리다이렉트, 배치) | 제외하고 관련 화면 비고에 기록 | 화면 수에 섞이면 범위가 왜곡됨 |
| 공통 컴포넌트(GNB·탭바·배너 영역) | 별도 공통 항목 또는 상위 화면 비고 | 화면마다 중복 등록하지 않음 |
| 같은 URL·같은 화면을 두 메뉴에서 진입 | 하나로 통합하고 진입 경로를 비고에 기록 | 중복 설계 방지 |
| 백업·빈 페이지·404 화면 | 정리 대상으로 별도 목록 | 현행 분석에서는 근거로 남김 |

제외·통합한 항목은 지우지 않고 별도 시트에 사유와 함께 남긴다. 나중에 "왜 빠졌는지"를 다시 찾을 수 있어야 한다.

<a id="screen-id"></a>
### 화면 ID와 채널

- 화면 ID는 프로젝트 규칙(영역-모듈-번호 등)을 따르고 한 번 부여한 ID는 재사용하지 않는다. 삭제된 화면은 '삭제' 상태로 남긴다.
- 같은 화면을 여러 모듈 아래 중복 정의하지 않는다. 다른 업무에서 같은 화면을 쓰면 하나를 원본으로 두고 권한·진입 경로로 구분한다.
- 앱(MA)·PC웹(PW)·모바일웹(MW)처럼 채널이 나뉘면 채널을 열로 표시하고, 채널별로 화면을 복제하지 않는다. 채널마다 동작이 다를 때만 차이를 비고에 적는다.
- 1차/2차 범위가 나뉘면 우선순위 열(P1·P2·P3)을 두고, 2차로 미룬 화면이 1차 화면의 진입·연결에 영향을 주는지 확인한다.

<a id="asis-tobe"></a>
### AS-IS↔TO-BE 대조

| 판정 | 기준 | 근거로 남길 것 |
| --- | --- | --- |
| 일치 | 화면명·기능이 같음 | 양쪽 ID |
| 명칭 변경 | 기능은 같고 이름만 다름 | 양쪽 ID, 판단 근거 |
| 통합 | 여러 AS-IS 화면이 하나의 TO-BE 화면으로 합쳐짐 | 대응 관계, 통합 방식(탭·필터 등) |
| AS-IS만(누락 후보) | TO-BE에서 대응 화면을 찾지 못함 | 처리 방향: 반영 / 의도적 제외 / 결정 필요 |
| TO-BE만(신규) | AS-IS에 없는 화면 | 신규 요구 근거 |

판정마다 **신뢰도(높음·중간·낮음)**를 붙인다. 화면 설명 없이 메뉴명만으로 판단했다면 신뢰도를 낮추고 '추정'으로 표시한다. 'AS-IS만'은 곧바로 누락으로 단정하지 않는다. 의도적으로 없앤 기능일 수 있으므로 처리 방향을 결정 필요로 남기고, 사업 결정이 필요한 항목은 [결정 기록](decisions.md)에 연결한다.

<a id="screen-spec"></a>
## 화면설계서 작성 기준

화면설계서는 개발·디자인·QA가 같은 화면을 같은 의미로 이해하게 만드는 문서다. 화면마다 아래 항목을 확인한다.

| 항목 | 확인할 내용 |
| --- | --- |
| 화면 정보 | 화면 ID·명칭·채널·진입 경로·이전/다음 화면 |
| 구성 요소 | 영역별 요소, 표시 데이터와 출처, 정렬·페이징·검색 조건 |
| 상태 | 초기·로딩·데이터 없음·오류·권한 없음·점검 상태의 표시 |
| 동작 | 버튼·링크별 결과, 확인 팝업, 성공·실패 메시지 |
| 입력 검증 | 필수 여부, 형식·길이, 중복 확인, 오류 문구 |
| 정책 참조 | 적용되는 정책 ID(취소·노출·승인 등)와 화면 내 반영 위치 |
| 미정 | 결정 필요 항목, 결정 주체, 임시 가정 |

화면에 보이는 필드만으로 데이터 구조를 확정하지 않는다. 표시 데이터의 출처·계산 방식이 불분명하면 개발 협의 항목으로 남긴다. 문구는 확정 문구와 가안을 구분한다.

<a id="policy"></a>
## 정책 정의와 상태

여러 화면에서 쓰는 업무 규칙은 정책 정의로 분리하고 화면설계서에서 참조한다.

- **주체와 조건:** 누가(회원 유형·관리자 권한) 어떤 조건(기간·채널·결제 수단)에서 무엇을 할 수 있는지.
- **상태와 전이:** 이용권·주문·프로모션 같은 대상의 상태 목록, 상태를 바꾸는 행위와 조건, 되돌릴 수 있는지.
- **예외:** 취소·부분 취소·만료·중복 요청·재시도·외부 연동 실패 때 사용자와 운영자가 보는 결과.
- **노출·우선순위:** 여러 혜택·프로모션이 겹칠 때 적용 순서와 중복 허용 여부.

정책 문장은 "~할 수 있다 / 없다"처럼 판정 가능하게 쓴다. "적절히", "필요시" 같은 표현은 결정 질문으로 바꾼다.

<a id="auth"></a>
## 권한·승인

- BO 메뉴는 조회·등록·수정·삭제·승인·다운로드 권한을 구분해 화면별로 표시한다.
- 승인이 필요한 업무는 요청자·승인자 지정 방식, 요청 사유 입력, 알림, 반려 후 처리, 승인 전 수정 가능 여부를 정한다. 프로젝트 공통 승인 패턴이 있으면 그 패턴을 참조하고 다른 점만 적는다.
- 같은 화면을 다른 조직(고객센터·운영·파트너)이 쓰면 화면을 복제하지 않고 권한으로 보이는 범위를 나눈다.

<a id="privacy"></a>
## 개인정보·보안

- 화면에 표시하는 개인정보 항목과 마스킹 기준, 엑셀 다운로드 시 사유 입력·이력 기록 여부를 화면별로 적는다.
- 회원 유형(내국인·외국인·기업 등)에 따라 수집 항목이 다르면 유형별로 구분한다.
- 실제 고객 데이터·운영 화면 캡처는 산출물 예시로 쓰지 않는다. 필요한 경우 가명 데이터로 바꾼다.

<a id="change"></a>
## 변경 관리와 개발 전달

- 확정된 IA·설계서를 바꾸면 변경 이력(일자·화면 ID·변경 내용·사유·요청자)을 남기고 영향받는 개발·QA 작업에 알린다.
- 개발에 전달하는 범위는 '확정 / 가안 / 결정 필요'로 구분한다. 결정 필요 화면을 확정처럼 전달하지 않는다.
- 개발 질의에 답할 때는 [공통 양식](decisions.md#request-template)으로 답변과 반영 위치를 남기고, 설계서에 반영했는지 확인한다.

<a id="review"></a>
## 검수·완료 근거

| 검수 항목 | 확인 방법 |
| --- | --- |
| 요구 반영 | 요구 목록의 각 항목이 IA 화면·정책에 연결되는가 |
| IA 일치 | IA의 화면 ID와 설계서의 화면 목록이 같은가 |
| 정책 일관성 | 같은 정책이 화면마다 다르게 쓰이지 않았는가 |
| 상태·예외 | 오류·빈 상태·권한 없음이 정의됐는가 |
| 미정 정리 | 결정 필요 항목에 주체·재개 조건이 있는가 |

검수 결과는 Pass / Fail / Not Run / N/A로 남기고, Not Run은 이유를 적는다. 기획 검수 통과와 현업 승인, 개발 반영 완료를 구분한다.
